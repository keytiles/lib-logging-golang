## TLDR

`kt_logging` is a thin, config-driven wrapper around [zap](https://pkg.go.dev/go.uber.org/zap). You:

1. Load a Python-style YAML/JSON config (`loggers` + `handlers`) via `InitFromConfig`
2. Optionally set **global labels** attached to every event
3. Obtain a named `Logger` with `GetLogger` / `With`
4. Log with `Printf`-style methods; add per-event labels via `WithLabel` / `WithLabels` → `LogEvent`

If you never call `InitFromConfig`, the first `GetLogger`/`With` creates a default **root** logger that writes JSON to stdout at info level. That lazy path is panic-free (hard fallback root if default construction fails).

## How the pieces relate

```text
                    ┌─────────────────────────┐
                    │  YAML / JSON config     │
                    │  loggers + handlers     │
                    └───────────┬─────────────┘
                                │ InitFromConfig
                                ▼
┌──────────────┐      ┌─────────────────────────┐
│ GlobalLabels │─────▶│  package logger registry │
│ (all events) │      │  map[name]*Logger        │
└──────────────┘      └───────────┬─────────────┘
                                  │ GetLogger / With
                                  ▼
                         ┌────────────────┐
                         │    Logger      │  name, level, handlers
                         │                │
                         │ WithLabel(s)   │──▶ LogEvent (temp labels)
                         │ Info/Warn/...  │──▶ log() ──▶ each zap.Logger
                         └────────────────┘
                                  │
                                  ▼
                         ┌────────────────┐
                         │   Handlers     │  (zap cores / outputs)
                         │ stdout, file,  │
                         │ rolling file   │
                         └────────────────┘
```

Relations in words:

- **Config → Handlers → Loggers**  
  Init builds one underlying `*zap.Logger` per named handler, then each named logger gets a map of those handlers by name. Logger config must reference existing handlers. A **`root`** logger is mandatory in config.
- **Logger names are hierarchical**  
  Dot-separated names (e.g. `controller.something`) resolve by walking parents; if a name is missing, a **clone** of the nearest ancestor (or `root`) is registered under that name (same level + handlers, different `name` field on events).
- **Labels attach in two scopes**  
  - Global: `SetGlobalLabels` / `GetGlobalLabels` — every event. Both copy: treat `Get` as a snapshot; always `Set` to publish changes (do not rely on mutating a previously returned slice).  
  - Per event: `Logger.WithLabel` / `WithLabels` → `LogEvent` — only that call chain  
  Every emitted event also gets a `logger` string field with the logger’s name.
- **Filtering is layered**  
  Logger level first (`None` / empty handlers → silent). Zap’s own handler level still applies on the wire. `Is*Enabled()` / `IsSilent()` reflect logger level **and** whether any handlers are attached.

## Typical usage flow

1. `kt_logging.InitFromConfig("./log-config.yaml")` (or `.json`)
2. Optionally `SetGlobalLabels([...])`
3. `logger := kt_logging.GetLogger("main")` or `kt_logging.With("main")`
4. `logger.Info("hello %v", x)` or `logger.WithLabel(...).Warn("...")`
5. Use `IsDebugEnabled()` (etc.) when building expensive messages

Message formatting uses `fmt.Sprintf` style. Formatting runs only after the logger decides the event is not filtered out (and has handlers).

## Log levels

Ordered from most restrictive to most verbose:

- `NoneLevel` (`none` / `off` in config) — logger emits nothing
- `ErrorLevel` (`error`)
- `WarningLevel` (`warning` / `warn`)
- `InfoLevel` (`info`)
- `DebugLevel` (`debug`)

Config level strings are case-insensitive. A log event is emitted only if `logger.level >= event level`.

## Configuration

Python-style: two maps — **loggers** and **handlers**. See `example/log-config.yaml`.

### Loggers

Each entry (map key = logger name):

- `level` — see above; `none`/`off` for silence by level
- `handlers` — list of handler names; empty list ⇒ no output (`IsSilent()` true even if level is high)

`root` must be defined.

### Handlers

Each entry:

- `level` — zap atomic level for that output
- `encoding` — `json` or `console`
- Either:
  - `outputPaths` — e.g. `stdout`, or a file path (standard zap build), **or**
  - `rollingFile` — lumberjack rotation (`file`, `maxSizeMb`, `maxAgeDays`, `maxBackups`, `compress`)  
    **Cannot** combine `rollingFile` with `outputPaths` on the same handler.

Encoder keys used: `message`, `level`, `time` (RFC3339 nano). Caller and stacktrace are disabled.

### Default config (no `InitFromConfig`)

On first logger access without prior init:

- Logger `root`: level `info`, handler `stdout_json`
- Handler `stdout_json`: JSON to `stdout`, level `info`

### Supported file extensions

- `.yaml`
- `.json`

Anything else fails at parse time.

## Core types & APIs

### Package-level

- `InitFromConfig(cfgPath string) error`
- `GetLogger(name string) *Logger` — create-or-get; hierarchical fallback
- `With(name string) *Logger` — alias of `GetLogger` for fluent style
- `SetGlobalLabels` / `GetGlobalLabels` — thread-safe; get/set copy (snapshot semantics)
- `PACKAGE_NAME` — `keytiles.lib.logging.kt_logging`

### `Logger`

- Identity / config: `GetName()`, `GetLevel()`, `GetHandlers()` (handlers map is a shallow copy)
- Log: `Log`, `Debug`, `Info`, `Warn`, `Error`
- Per-event labels: `WithLabel`, `WithLabels` → `LogEvent`
- Gates: `IsErrorEnabled`, `IsWarningEnabled`, `IsInfoEnabled`, `IsDebugEnabled`, `IsSilent`

### `LogEvent`

Value type (stack-friendly). Collects labels with `WithLabel` / `WithLabels`, then fires with `Debug` / `Info` / `Warn` / `Error`. Labels apply only to that event.

### `Label`

Atomic types only (string, bool, int64, float64) — no nested objects/arrays as label values (serialize complex data to a JSON string if needed). Constructors: `StringLabel`, `IntLabel`, `FloatLabel`, `BoolLabel`. Getters available since 2.1.0.

## Hierarchy behavior (important)

`GetLogger("a.b.c")`:

1. If `a.b.c` exists in the registry → return it
2. Else recurse to parent `a.b`, then `a`, then `root`
3. Clone that ancestor’s level + handlers, set `name` to the requested name, register, return

So `controller.something` with only `controller` in config inherits `controller`’s level and outputs, but events carry `logger: "controller.something"`.

Registry access is protected by a mutex around `GetLogger`.

## Known limitations

- **Rolling files on Windows** — lumberjack can hit “file is being used by another process”; not reliable on Windows. Prefer non-rolling outputs there (see `CHANGELOG.md` release 2.0.0).
- Handlers are zap loggers; logger-level filtering happens in this package first, then zap may filter again by handler level.
