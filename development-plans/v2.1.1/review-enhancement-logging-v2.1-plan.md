# Review & enhancement plan — logging (`kt_logging`) v2.1

## Meta

- Generated / last modified: 2026-07-20 02:50
- This doc was generated by AI agent
- Scope: code review of `pkg/kt_logging` — panic/crash risks first, then CPU / memory opportunities
- Companion feature doc: [`docs/logging-v2.1.md`](../../docs/logging-v2.1.md)
- Library release line: **2.1.x** (this plan lives under `development-plans/v2.1.1/`)

## Panic policy (refined)

- **Startup is allowed to panic** — e.g. while the app calls `InitFromConfig` / reads config. Failing fast during boot is acceptable.
- **Runtime must not panic** — once the process is past startup, `GetLogger` / `With` and any log emit (`Info`, `Warn`, `WithLabel`, …) must not panic. These can be called at any later point in the app lifetime.

## Goals

- Eliminate **runtime** panic paths on `GetLogger` / `With` and logging (not startup/config)
- Identify **CPU and memory** waste on hot logging paths and in registry / label handling
- Capture a prioritized, phased backlog ready for later implementation

## Non-goals (this document)

- Implementing the fixes (document findings + backlog only)
- Changing zap as the underlying backend
- Redesigning the public API surface beyond what fixes require
- Making `InitFromConfig` panic-free (startup panic is OK; returning `error` remains a nice-to-have, not a must)

## Findings — Panic & crash risks

### P0 — Runtime panic paths (`GetLogger` / logging)

These can fire long after startup and are the primary targets.

#### P0.1 — Explicit panic on lazy default init (inside `GetLogger`)

- **Where:** `getLogger` when `loggers == nil`: panics if `initLoggersFromConfig(getDefaultLoggerConfig())` fails
- **Problem:** First `GetLogger` / `With` without prior `InitFromConfig` is a **runtime** path (any time). Default init currently uses `zap.Must`; a build failure becomes a panic from a getter, not from startup.
- **Recommended fix:** Never `panic` from this path. Ensure lazy default init always installs a usable root (hardcoded safe fallback if needed). Prefer constructing a minimal stdout JSON root without going through a panicking helper.

#### P0.2 — Explicit panic in `getRootLogger` (used from `GetLogger`)

- **Where:** `getRootLogger` panics if `"root"` is missing from the registry
- **Problem:** Invoked while resolving logger names. Should be unreachable after successful init, but can surface under races (see P1.1) or init bugs — still on the **runtime** path.
- **Recommended fix:** Fall back to creating/installing a safe default root without panic; keep `"root"` mandatory for file-based `InitFromConfig` validation at startup.

### P1 — Concurrency issues (races on runtime paths)

#### P1.1 — `InitFromConfig` does not take `loggersLock`

- **Where:** `InitFromConfig` assigns `loggers = configuredLoggers` unlocked; `GetLogger` mutates the registry under `loggersLock`
- **Problem:** Data race when init overlaps with later (or concurrent) `GetLogger` use. Can make `"root"` appear missing and hit P0.2.
- **Recommended fix:** Hold `loggersLock` for the registry swap. (Init itself may still panic/fail fast — that is fine; the race with runtime getters is not.)

#### P1.2 — Global labels unsynchronized

- **Where:** `SetGlobalLabels` / `GetGlobalLabels` / `Logger.log` reading `zapGlobalLabels` — no lock
- **Problem:** Concurrent set + log is a data race on the **logging** path. `GetGlobalLabels` returns the **live** backing slice; callers can mutate it while logging (get → append → set on the same slice).
- **Recommended fix:** Protect with a mutex or `atomic.Value`; return a **copy** from `GetGlobalLabels`; document snapshot semantics.

#### P1.3 — `GetHandlers()` exposes internal map

- **Where:** `Logger.GetHandlers()` returns `l.handlers` directly
- **Problem:** External mutation races with `log()` ranging over handlers (runtime).
- **Recommended fix:** Return a shallow copy of the map, or document strictly as read-only (copy is safer).

### Accepted at startup (not P0)

Panic / hard-fail during config load is **acceptable** per panic policy.

#### S.1 — `zap.Must` during `InitFromConfig`

- **Where:** `initLoggersFromConfig` non-rolling branch: `zap.Must(zapCfg.Build())`
- **Status:** Accepted if it only runs from startup `InitFromConfig`. Optional nicety: return `error` instead of panic for cleaner app boot handling — **not required** for this plan’s panic goal.
- **Caution:** The same helper is also used for lazy default init from `GetLogger` (P0.1) — that runtime use must not panic even if startup keeps `zap.Must`.

#### S.2 — Config parse / validation failures

- Invalid YAML/JSON, missing `root`, bad handler refs, etc. returning errors (or panicking) during `InitFromConfig` is fine.
- Optional: validate rolling `encoding` and return config error; still startup-only.

### Lower / edge (document; lower priority)

#### L.1 — `ioutil.ReadAll` error ignored

- **Where:** `pkg/kt_logging/config.go` → `parseFromJsonOrYaml`
- **Problem:** Read errors ignored; confusing parse failures. `ioutil` deprecated.
- **Recommended fix:** Check and return read errors; prefer `io.ReadAll`. (Startup path — quality improvement, not panic-policy critical.)

#### L.2 — Nil `*Logger` receiver

- **Where:** `(*Logger).Info` / etc.
- **Problem:** Nil receiver panics. Public `GetLogger` / `With` normally never return nil.
- **Recommendation:** Caller contract — no change required unless defensive guards are desired later.

#### L.3 — Unknown `LogLevel` in `log()`

- **Where:** `Logger.log` `default` branch re-logs at `WarningLevel`
- **Problem:** None for panic — Warning is a known case; no infinite recursion.
- **Recommendation:** Keep as intentional behavior; optional clearer message later.

## Findings — CPU / memory

### Hot path allocations

#### M.1 — Empty slice literals on every log

- **Where:** `Logger.Debug` / `Info` / `Warn` / `Error` / `Log` pass `[]Label{}` into `log`
- **Problem:** Allocates an empty slice at the call site **before** level filtering inside `log`.
- **Recommended fix:** Pass `nil` instead of `[]Label{}`.

#### M.2 — `fmt.Sprintf` always

- **Where:** `Logger.log` always does `fmt.Sprintf(message, messageParams...)`
- **Problem:** Unnecessary work/alloc when there are no message params.
- **Recommended fix:** If `len(messageParams) == 0`, use `message` as-is.

#### M.3 — Field slices grow from zero capacity

- **Where:** `joinedLabels` in `log`; `toZapFieldArray` starts as `[]zap.Field{}`
- **Problem:** Repeated growth reallocations on every emitted event.
- **Recommended fix:** Pre-allocate, e.g. `make([]zap.Field, 0, 1+len(zapGlobalLabels)+len(customLabels))` (and same idea inside `toZapFieldArray`).

#### M.4 — `LogEvent` double-buffering

- **Where:** `LogEvent` keeps `customLabelList [][]Label` and `customLabels []Label`, then flattens to another `[]Label`, then converts to `[]zap.Field`
- **Problem:** Extra slices and copies on the labeled hot path.
- **Recommended fix:** Simplify to a single `[]Label` (append in `WithLabel` / `WithLabels`), or build zap fields once.

#### M.5 — `newLogEvent` allocates empty slices

- **Where:** `newLogEvent` sets `customLabelList = [][]Label{}` and `customLabels = []Label{}`
- **Problem:** Unnecessary allocs; `append` works on nil slices.
- **Recommended fix:** Leave fields nil until first `WithLabel(s)`.

#### M.6 — `GetLogger` always uses exclusive `Lock`

- **Where:** `GetLogger` always `loggersLock.Lock()` even for cache hits
- **Problem:** Unnecessary writer contention under high concurrent `With("fixedName")` usage.
- **Recommended fix:** `RLock` for lookup; take write lock only on miss/create (double-checked locking).

#### M.7 — Hierarchy `clone()` and unbounded registry

- **Where:** `getLogger` clones parent and registers every new name; `clone()` copies the handlers map
- **Problem:** Clone cost is fine for rare misses. Registry **grows unboundedly** with unique dynamic logger names → long-lived process memory growth.
- **Recommended fix (docs / future):** Document “reuse stable names”; optional later: max-cache or no auto-register mode. No urgent code change for typical package-name usage.

### Secondary

#### M.8 — Benchmark measures registry + log together

- **Where:** `tests/benchmark_test.go` calls `With("main")` every iteration
- **Problem:** Always hits the registry lock; understates / confuses pure emit cost.
- **Recommended fix:** Cache `GetLogger` outside the loop for the hot-path bench; add a second bench for cached logger + labels.

#### M.9 — Invalid rolling `encoding` silently defaults to JSON

- **Where:** rolling-file branch: only `"console"` vs else → JSON
- **Problem:** Not a panic/perf issue; weak validation (typos become JSON).
- **Recommended fix:** Optional startup improvement — validate encoding in `InitFromConfig` and return/fail config error.

## Recommended phases (implementation backlog)

### Phase 1 — Panic-safe runtime (`GetLogger` / resolve)

- Remove panics from lazy default init inside `getLogger` (safe fallback root; do not use panicking helpers on this path)
- Remove panic from `getRootLogger` (install/fallback default root)
- Lock around `InitFromConfig` registry swap so runtime getters cannot race with init (P1.1)
- Optional (startup quality, not panic-policy): `ReadAll` error check, encoding validation, `Build()`+error instead of `zap.Must` **only for** `InitFromConfig`

### Phase 2 — Thread-safe globals & encapsulation

- Synchronize global labels (mutex or `atomic.Value`)
- `GetGlobalLabels` returns a copy; document snapshot semantics
- `GetHandlers` returns a shallow copy (or equivalent hardening)

### Phase 3 — Hot-path allocations

- Pass `nil` empty labels from `Debug`/`Info`/…
- Skip `Sprintf` when no args
- Pre-size zap field slices
- Simplify `LogEvent` label storage
- Leave `newLogEvent` slices nil by default
- `RWMutex` / double-checked pattern for `GetLogger`

### Phase 4 — Docs + benches

- Update [`docs/logging-v2.1.md`](../../docs/logging-v2.1.md) “What changed vs previous” when phases land (same unreleased plan / 2.1 line — grow in place)
- Improve benchmarks (cached logger vs registry hit)
- Document unbounded logger-registry guidance for consumers
- Document panic policy: startup may fail hard; `GetLogger` / logging must not panic

## Out of scope / accepted risks

- **Startup panics** during `InitFromConfig` / config parse (including `zap.Must` on that path) — accepted
- Windows rolling-file / lumberjack lock issue (already known; see `CHANGELOG.md`) — not addressed here
- Replacing zap or changing Python-style config shape
- Making nil `*Logger` methods no-ops (caller misuse)
- Hard caps on logger registry size (optional future; document for now)
