## Why are we doing this?

- `GetLogger` / `With` previously cached **every** new hierarchical name forever.
- That is fine for a small set of package names, but as a library we must not allow unbounded memory growth if callers misuse dynamic names (or simply create many distinct hierarchical names over a long process life).
- Loggers defined in config must remain permanent (re-running config to recreate them is wrong).

## What will be changed?

- Split registry entries into:
  - **Pinned** — from `InitFromConfig` (and lazy/hard-fallback `root`) — never evicted
  - **On-demand** — created when resolving a name not already in the registry (hierarchical clone of parent) — subject to a size limit tracked by `loggersCreationOrder` (FIFO)
- New top-level config field: **`loggerMaxCacheSize`**
- Default **3000** when omitted or `0`; negative values rejected at init
- Docs: README + example YAML comments + feature doc — plain language (no “auto logger” jargon)
- Tests covering pin / evict / recreate / config override

## Decisions we made

- Approach: **bounded on-demand cache** (not soft-warn, not hard-fail, not heuristics, not “don’t cache at all”)
- Eviction policy: **FIFO by creation order** (`loggersCreationOrder` slice; index 0 = oldest) — simpler than true LRU; enough for a memory ceiling
- Config loggers (and init `root`) stay forever because they are **never** added to `loggersCreationOrder`
- Public config name: **`loggerMaxCacheSize`** (not `autoLoggerCacheMax` — “auto” was unclear)
- Default size **3000** (~few MB worst case; on-demand entries share zap handler instances)
- On cache full: evict oldest **on-demand** entry, then register the new name; `GetLogger` still returns a correctly named logger
- Cache hits do not reorder (creation order only)
- `InitFromConfig` resets registry + creation-order slice
- No separate `pinnedLoggers` set — eviction candidates are only names in `loggersCreationOrder`

## Notes / how to explain it (user-facing)

Preferred minimal wording (README / comments):

- Loggers listed under `loggers:` stay in memory for the life of the process.
- If you call `GetLogger` / `With` with a name that is **not** in the config, the library creates a logger that inherits from its parent (hierarchy) and **caches** it.
- `loggerMaxCacheSize` limits how many of those **extra** (non-config) names are kept. When the limit is reached, the oldest extra names (creation order) are removed from the cache. Logging still works — the next `GetLogger` for that name creates it again.

Example YAML comment to ship with visible configs:

```yaml
# loggerMaxCacheSize: max cached loggers for names NOT listed under loggers:.
# Config loggers are always kept. Over the limit, oldest non-config names
# (creation order / FIFO) are dropped from the cache (recreated on next GetLogger if needed).
# Omit or 0 = default 3000.
loggerMaxCacheSize: 3000
```
