## Why are we doing this?

- Today init only accepts a **file path**, but the real unit of configuration is already `ConfigModel`.
- Callers should be able to build / load / tweak a `ConfigModel` in code (tests, embeds, dynamic assembly) and apply it.
- We also want a path toward **runtime** inspection (`GetCurrentConfigModel`) and re-apply after edits — without silently leaving stale `*Logger` pointers on the wrong settings.

## What will be changed? (agreed)

### Init API split (backward compatible)

- Add **`InitFromConfigFile(cfgPath string) error`** — parse YAML/JSON → `InitFromConfigModel`
- Add **`InitFromConfigModel(config ConfigModel) error`** — resolve `loggerMaxCacheSize`, `initLoggersFromConfig`, `resetRegistry` under lock (current post-parse body)
- Keep **`InitFromConfig(cfgPath string) error`** as a thin wrapper → `InitFromConfigFile`
  - Mark **`Deprecated: use InitFromConfigFile`** (godoc)
- Migrate in-repo callers (example, README, tests/benches) off the deprecated name

### Config snapshot

- Add **`GetCurrentConfigModel() (ConfigModel, bool)`** (or `(ConfigModel, error)` / ok flag)
  - Returns a **copy** of the last successfully applied model (so callers can mutate safely then re-init)
  - `ok=false` / empty if never initialized via Init* (lazy-default-only path may synthesize a model equivalent to `getDefaultLoggerConfig()` — decision TBD with runtime approach)

## The runtime problem (your analysis is correct)

`Logger` today owns concrete `level` + `handlers`:

```go
type Logger struct {
	name     string
	level    LogLevel
	handlers map[string]*zap.Logger
}
```

Every `Init*` path builds **new** `*Logger` values and **replaces** the registry. Callers that already hold `*Logger` from an earlier `GetLogger` keep pointing at the **old** objects. Re-init alone does **not** update those pointers. On-demand clones are separate objects too (`clone()` copies level/handlers).

So “edit model → InitFromConfigModel again” only helps code that **re-fetches** loggers (or never cached pointers).

## Options for runtime configurability (simplest → more capable)

### Option E — Re-init without wiping the map + `loggerCacheItem` (clarified)

**Intent (corrected):** On `InitFromConfigModel` / reload we do **not** empty or replace the whole registry map. We **keep** existing entries and **realign** them to the new `ConfigModel` (mutate `*Logger` level/handlers in place where names still apply). We **still delete** from the map when on-demand `loggerMaxCacheSize` is exceeded (FIFO) — that bound stays.

Sketch:

```go
type loggerCacheItem struct {
	logger       *Logger
	creationTime time.Time
	// maybe: fromConfig bool
}
var loggers map[string]*loggerCacheItem
// lastApplied ConfigModel for GetCurrentConfigModel
```

Pieces:

1. Keep effective `ConfigModel` always (for `GetCurrentConfigModel`).
2. **Reload:** walk new config; for each name, if `loggers[name]` exists → update that `*Logger` in place; else create and insert. Do **not** `loggers = newMap` wholesale.
3. **On-demand after reload:** either re-derive from new parents (mutate descendants) or drop only on-demand entries / rebuild them on next `GetLogger` — policy TBD; config-named pointers stay valid either way.
4. **`creationTime`:** can recompute FIFO order by sorting non-config items; optional vs keeping `loggersCreationOrder` slice.
5. **FIFO eviction:** when over max, still `delete` oldest on-demand from the map (unchanged memory goal).

#### What this achieves

- Held `*Logger` for **config names that remain** in the new model keep working after reload (same pointer, new settings).
- Memory bound for on-demand names preserved via eviction-on-exceed-max only.
- Same concurrency caveat as Option B: mutate safely vs concurrent emit.

#### Remaining culprits (still real)

1. **Name removed from config** — leave old entry? remove and orphan held pointers? mark silent?
2. **On-demand clones** after parent change — need explicit realign or clear-on-demand-only on reload.
3. **Evicted on-demand + held pointer** — still orphaned; reconfig cannot find them (acceptable under cache contract).
4. **Handler rebuild races** — swapping `handlers` while emitting.

#### Relation to A/B/C

- This **is Option B**, with clearer wording: wipe-on-init goes away; FIFO delete-on-overflow stays.
- Not Option C (no name-handle indirection).
- Not “unbounded map.”

## Recommendation (for discussion)

- Ship **InitFromConfigFile / InitFromConfigModel / deprecate InitFromConfig / GetCurrentConfigModel** (store last-applied model).
- Runtime lean: **Option B / E (clarified)** — re-init realigns in place; FIFO still evicts on-demand over max — if we care that cached **config** loggers follow reload.
- Prefer **Option C** only if every hierarchical/`GetLogger` handle must follow without special on-demand policy.
- Prefer **Option A** if reload is rare and callers can re-`GetLogger`.

## Decisions we made

- Init API split + deprecate `InitFromConfig` — **yes**
- `GetCurrentConfigModel` returning a copy — **yes**
- On reload: **do not empty the map**; realign existing loggers (clarified Option E / B) — **leaning yes**, finalize vs A/C
- FIFO delete when over `loggerMaxCacheSize` — **unchanged yes**
